# 指示書：地方（浦和）で「当たりやすさ」を確かめて精度に入れるシステム

## 1. 調査結果：可能か → **可能**

**今できていないこと**
- 今の地方ベース（nar-local-v1）は、当日の出走馬自身の戦績だけで学習している。同じレースの他の馬がそろわないので、「上位5頭ボックスが何%当たるか」「信頼度Aは本当に当たりやすいか」を、レース単位で測れない。

**できる理由**（2026-11-25 に確認）
- **データの量**：集めた戦績に出てくる浦和の開催は、2026-05 以降で 28日・260レース、8月以降で 13日・125レースあった。浦和は月に約5日・約60レース。5月〜11/25 を集めれば、約30日・約350レースになる。学習と検証に分けても足りる量である。南関東の4場（浦和・大井・川崎・船橋）まで広げれば、8月以降だけで約65開催日ある。
- **読み取り**：地方の結果ページ（着順・払戻）は 11/24 に本番で正しく読めた。単勝〜三連単の払戻表も正しく読めた。
- **一覧**：地方の一覧ページから、競馬場ごとの全レースを読む処理（`keiba_nar.venue_races`）は動いている。
- **戦績**：各馬の戦績は db.netkeiba の馬ページで、JRA と同じ仕組みで取れる。地方の走も載っている。
- **流用できる仕組み**：JRA ダートの「過去レースの検証データ収集」（keiba_backtest）と、全頭そろったレースでの検証（accuracy_experiment・dirt_test）。地方用の切り替えを足せば使い回せる。

**取得の量と時間の見込み**
- 浦和の約350レースで、結果ページが約350件、馬ページが約1,200〜1,500件。
- JRA ダートの315レースは4〜5時間かかった。同じ程度で、取得先の制限で止まれば待つ分だけ延びる。
- 取得はすべて本番の共通ゲートを通す。支払いや個人情報は発生しない。

**限界**
- 地方の一般の格付け（C1・B2 など）は、今のクラス水準に入っていない。必要なら、別の候補として事前に登録してから加える。
- 過去の払戻は、結果ページを読み直すときに取れる（取得の回数は同じ）。

## 2. プロンプト（ここから下を送る）

競馬分析ラボ（sukekyou0214/keiba-analysis-lab、ブランチ claude/keiba-lab-handover-5g9drw）で、
**地方（まず浦和）でのレース単位の当たりやすさを確かめるシステム**を作り、確かめた結果を予想と信頼度に入れてください。

### 守ること
- 予想はラボの計算だけで出す。AIが馬やレースを選ばない。
- 取得は本番アプリの共通ゲートだけを通す。直接の取得や、制限を回避することはしない。拒否されたら待つ。止まった状況は正直に報告する。
- 生データは GitHub に置かない。置いてよいのは、集計・検証ログ・レース前の記録だけ。
- 計算する前に、`docs/accuracy/00-plan-and-preregistration.md` へ期間・候補・判定の規則を書いてコミットする。検証期間は1回だけ見る。
- 点数を確率として表示しない。信頼度の的中率は、過去の検証で出た実績として書く（「当たる確率」とは書かない）。
- PR → CI 通過 → スカッシュマージ → `git merge -s ours origin/main`。

### 手順

**A. 収集の仕組みを地方に対応させる（コード）**
1. `keiba_backtest.run` に、取得先（`JRA`／`地方`）と競馬場を足す。
   - 地方のときは、一覧に `keiba_nar.NAR_LIST_URL` と `keiba_nar.venue_races(…, 競馬場)` を、結果に `keiba_nar.NAR_RESULT_URL` を使う。
   - 公表ペースの取得は、地方では行わない（JRA 専用のため）。
   - 結果の `info` に払戻（`parse_payouts`）がそのまま入ることを確かめる。
2. 管理・検証の画面（過去レースの検証データ収集）に、「取得先：JRA／地方」と「競馬場」の入力を足す。`scripts/ops/backtest_prod.js` には `BT_SOURCE` と `BT_VENUE` を足す。
3. テストを足す：保存済みの地方の一覧の HTML で `venue_races` を確かめる。地方の結果ページの形（全頭の表・払戻）は小さな見本で確かめる。既存のテストを全部通す。

**B. 事前登録（データを見る前）**
`00` に追記する。
- **データ**：浦和、2026-05-01〜2026-11-25 の全レース（ダート）。開催日は、集めた戦績に出てくる浦和の開催日から決める（一覧の空振りで取得を無駄にしないため）。
- **期間**：学習 5/1〜8/31、検証 9/1〜11/25（1回だけ）。
- **候補**
  - `nar-v1`：dirt-v1 と同じ特徴量・同じ作り方（全頭そろったレースでの条件付きロジット）で、浦和の走で学習する。
  - 比べる相手：当日の出走馬の戦績だけの nar-local-v1、近走人気だけ、無作為。参考として当日の人気。
- **レース単位の指標**：上位3頭に勝ち馬、予想1位の3着以内、三連複5頭ボックスの的中（＝三連単5頭ボックスの的中）。
- **採用の規則**：nar-v1 − 近走人気だけ（上位3勝ち馬）の95%区間（2,000回、種0）の下限が0を上回れば、主予測にする。上回らなければ、今の方式のままにする。
- **当たりやすさ（信頼度）の確かめ方**
  - 今の区分（ボックス向きの順で A＝各日上位3／B＝4〜6／C＝7以下、地方の戦績の少ない馬が2頭以上で1段下げ）を、検証期間に1回当てはめる。
  - 「A の5頭ボックス的中率 − 全レース」の95%区間の下限が0を上回れば、区分を「地方で確かめ済み」とする。
  - 上回らなければ、区分の選び方の候補（頭数だけ／点差だけ／両方）を学習期間で選び直し、検証で1回確かめる。
- **回収率**：実際の払戻で、三連複5頭ボックス（10点）と三連単5頭ボックス（60点）の、区分別の回収率を出す。回収率は記録するだけで、採用の判断には使わない。

**C. 収集（本番）**
- `BT_SOURCE=地方 BT_VENUE=浦和 BT_WORK=urawa2026 BT_DATES=<開催日のカンマ区切り> node scripts/ops/backtest_prod.js start`
- 1回に取得できる上限で止まったら、続きから再開する。取得先から拒否されて止まったら、制限が明けるまで待って再開する（2回続けて拒否されたら、止めて報告する）。
- 完了したら ZIP を取り、空のフォルダに展開する。

**D. 検証（スクリプト `scripts/nar_backtest_test.py` を新しく作る）**
- `dirt_test.py` を元にして、上の候補・指標・規則どおりに計算する。
- 出力：`summary.csv`、`per_race_metrics.csv`、区分別の表（レース数・5頭ボックス的中率・三連複と三連単の回収率）、`run_log.json`。
- 結果を `docs/accuracy/14-nar-urawa.md` にまとめる（採用・不採用と、その理由）。

**E. 予想と信頼度に入れる**
- **nar-v1 が採用なら**：`scripts/nar_local.py` の順位を nar-v1 に替える（モデルは `models/nar_v1.json`。学習は全期間でやり直す）。
- **区分が「地方で確かめ済み」なら**：HTML の信頼度表に「過去の浦和（9/1〜11/25）での5頭ボックス的中：A ◯%・B ◯%・C ◯%、全レース ◯%」を添える。
- **確かめられなかったら**：「地方では未確認」の表示を残し、何が足りなかったかを書く。
- 指示書 `docs/ops/浦和全レース予想_指示書.md` を、新しい方式に合わせて更新する。

**F. 前向きの記録（その後ずっと）**
- 浦和の開催日ごとに、レース前の記録と結果の照合を `records/predictions/<日付>_urawa_local/` に残す。
- 区分別の的中と回収率を累計する。100レースたまったら、事前登録の規則で1回だけ見直す。

### 報告のしかた
- 先に結論を書く：使えるか・使えないか、レース単位の的中率、信頼度別の的中率、回収率。
- 数字は「過去の検証での実績」と書く。将来の保証として書かない。
- かかった時間、取得の件数、止まった回数とその理由を書く。

## 3. 進め方の目安
1. A（コード）：1〜2時間。PR・CI・マージのあと、本番に反映されるのを待つ。
2. C（収集）：4〜6時間（取得先の制限で止まれば延びる）。浦和の開催がない日にやると、当日の取得とぶつからない。
3. B・D・E：1〜2時間。
4. 南関東の4場に広げる場合は、浦和が終わってから同じ手順で行う（事前登録は別に書く）。
